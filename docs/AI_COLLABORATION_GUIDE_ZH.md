# Perspective Puzzle AI 协作运行手册

本文记录本项目中用户、Codex 与 Claude Code（DeepSeek V4 Flash 后端）的稳定协作方式，以及实际开发中得到的经验。它是协作流程的中文总入口；具体产品、架构和任务状态仍分别以 `PRODUCT.md`、`ARCHITECTURE.md`、`DECISIONS.md` 和根目录 `TASKS.md` 为准。

## 1. 协作目标

这套方式不是让多个模型同时自由修改项目，而是把不同能力放在合适的位置：

- 用户负责产品直觉、审美判断、试玩感受和最终取舍。
- Codex 负责把模糊想法收敛为规格，做架构决策、拆分任务、研究公开仓库、审查代码和验收结果。
- Claude Code / DeepSeek V4 Flash 负责边界清晰的大量代码编写、重复性修改和指定的局部修复。
- Unity 编译、自动测试、确定性截图和人工试玩提供事实证据，模型自己的“已经完成”不算验收。

三者共享同一个项目文件夹。文件是共同工作台，避免在不同聊天窗口反复复制大段上下文。

## 2. 为什么采用这种分工

DeepSeek V4 Flash 在目标文件、接口、算法和验收条件已经明确时，代码产出速度和性价比很好；当需求含糊、文件范围开放、还需要同时做产品决策时，它更容易长时间探索、扩大改动或给出看似完整但难以验收的结果。

Codex 的主要价值不是代替它写每一行代码，而是提前消除歧义，并在完成后检查真实差异和运行结果。用户不需要充当两个模型之间的人工提示词搬运工。

## 3. 标准工作循环

每轮开发固定经过以下流程：

1. 用户描述希望达到的体验、问题或视觉效果。
2. Codex 检查当前项目，确认产品与架构边界。
3. Codex 把一个可独立验收的实现合同写入 `tasks/ACTIVE.md`。
4. 用户在项目目录中保持一个 Claude Code 会话，并发送固定短指令：

   ```text
   Execute tasks/ACTIVE.md. Start with the requested edit and follow CLAUDE.md.
   ```

5. DeepSeek 只读取和修改合同点名的文件，完成后返回简短报告。
6. Codex 阅读真实文件和差异，运行对应编译、测试或截图检查。
7. 通过后更新正式任务板；失败则把精确错误变成一个更小的修复合同。
8. `tasks/ACTIVE.md` 恢复为 `IDLE`，或直接替换成下一项合同。

任何时候都只允许一个活动实现合同，避免两个代理同时修改同一系统。

## 4. DeepSeek 配置基线

Claude Code 的四个模型入口必须使用完全相同的模型字符串：

```json
{
  "ANTHROPIC_MODEL": "deepseek-v4-flash",
  "ANTHROPIC_DEFAULT_HAIKU_MODEL": "deepseek-v4-flash",
  "ANTHROPIC_DEFAULT_OPUS_MODEL": "deepseek-v4-flash",
  "ANTHROPIC_DEFAULT_SONNET_MODEL": "deepseek-v4-flash"
}
```

本机实现任务使用 `effortLevel: max`。不要在本项目中使用 `deepseek-v4-flash[1m]`：它曾在 T-001 中造成 Claude Code 请求挂起，而且与普通模型名混用会形成不同的缓存通道。

API Key 只保存在用户级 Claude Code 配置或环境变量中。严禁把 Key 写入项目文档、脚本、任务文件、Git 历史或聊天报告。

## 5. 缓存命中策略

DeepSeek 的上下文缓存依赖从第一个 token 开始重复的请求前缀。中间有相似内容并不足以命中。因此，本项目遵循这些规则：

- 连续的项目任务使用同一个 Claude Code 会话；终端关闭后恢复原会话。
- `CLAUDE.md` 保持短小、稳定，不在每一轮重写角色和规则。
- 变化内容统一放在 `tasks/ACTIVE.md`，聊天里只发送固定短指令。
- 不在提示词里粘贴完整产品文档、聊天记录、Unity 构建日志或截图描述。
- 大型动态输出写入 `Logs` 或 `outputs`，只让代理按路径读取需要的片段。
- 不在同一工作流中切换模型名、别名或供应商地址。
- 日常顺序开发不启用 Agent Teams。每个子代理是独立上下文，会把缓存拆成多条通道。
- 只有任务完全无关、当前会话被大量无效工具输出污染，或 Codex明确要求清理上下文时，才开启新会话。

`max` 思考强度本身不会直接破坏输入缓存，但会产生更长的工具循环和更多动态上下文。因此它适合规格明确的实现，不适合用来弥补模糊需求。

## 6. 合格的实现合同

DeepSeek 收到的任务应当满足：

- 一个清晰责任；
- 通常只修改一至三个文件；
- 目标类型、方法签名或现有模式已经指定；
- 产品与架构决策已经完成；
- 明确禁止修改的范围；
- 有确定的通过/失败信号；
- 代码差异可以由 Codex 一次审查完。

推荐写入 `tasks/ACTIVE.md` 的格式：

```text
Status: IN PROGRESS
Mode: IMPLEMENT, not plan or research

Read only:
- <必要文件>

Edit only:
- <目标文件>

Contract:
- <接口、行为、边界条件和算法>

Forbidden:
- 不修改其他文件
- 不增加依赖
- 不改变架构
- 不更新任务板
- 不运行未指定的大型测试

Verification:
- <如果分配给 DeepSeek，则写明确命令或结果>

Return only:
- files changed
- one notable assumption
- concrete risks
```

## 7. 验收规则

验收依据按改动类型选择：

- 纯 C# 领域逻辑：聚焦的 EditMode 测试。
- Unity 编辑器工具：批处理编译、明确退出码和生成物检查。
- 场景或视觉修改：固定分辨率截图并由 Codex 实际查看。
- 交互功能：PlayMode 测试加用户人工试玩。
- Bug 修复：原来失败的测试、编译错误或复现步骤必须转为通过。
- Windows 交付：构建成功后做启动烟雾测试。

DeepSeek 报告“应该可以编译”或“已经实现”只代表它结束了任务，不代表任务通过。

## 8. 失败恢复

出现问题时不要把整个项目重新讲一遍。Codex 先收集：

- 当前现象；
- 预期行为；
- 精确控制台错误；
- 涉及文件；
- 已经确认无误的部分。

然后把它缩成新的局部修复合同。连续十五分钟没有产生可用差异，通常说明任务仍然太大、接口不清楚、模型进入无效工具循环，或外部进程卡住。此时应停止并缩小任务，而不是继续增加提示词篇幅。

断网或终端关闭后，先确认文件是否已落盘、Unity 是否仍在运行，再恢复原 Claude Code 会话。不要因为一次断线就重新启动多个代理重复实现。

## 9. 已验证的经验

本项目目前已经验证以下做法有效：

- 先把投影逻辑做成与 Unity 场景无关的纯领域层，再连接交互表现，测试更可靠。
- 画风垂直切片必须通过实际渲染图审查，代码结构正确不能证明画面像产品。
- DeepSeek 更适合实现已经决定的局部模块；产品效果、镜头、反馈优先级由用户与 Codex 先收敛。
- 公开仓库主要用于研究成熟的交互和渲染做法，不应直接拼装整套第三方系统；任何复制或依赖都必须先核查版本与许可证。
- 稳定文件前缀、固定短指令和持续会话，比每次构造新的“完美长提示词”更利于缓存和成本控制。
- 任务状态只能在实际验收后更新，避免代理报告与仓库事实脱节。

## 10. 开工与结束检查表

开工前确认：

- 当前只有一个 `IN PROGRESS` 任务；
- `tasks/ACTIVE.md` 合同足够小且无产品歧义；
- 四个模型入口都是 `deepseek-v4-flash`；
- Claude Code 位于项目根目录并延续原会话；
- 提示词中没有 API Key 和大型动态日志。

结束前确认：

- 查看真实改动，而不是只读代理总结；
- 完成与风险相称的测试或视觉检查；
- 没有意外修改生成目录和无关文件；
- 没有新增未记录的第三方代码或依赖；
- 任务板、限制和下一任务与实际状态一致；
- `tasks/ACTIVE.md` 已清空或替换。
