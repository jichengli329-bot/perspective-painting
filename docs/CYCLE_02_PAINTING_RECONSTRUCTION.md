# Cycle 2 — 立体景物重构二维绘画

## 结论

第二周期不再优化 5×5 方块填格。现有版本保留为技术原型，新周期验证真正的产品命题：玩家摆放可识别的三维景物，利用透视、远近大小、轮廓重叠和遮挡，从指定镜头重构一幅完整的二维画面。

周期只做一幅原创风格化山水。完成标准不是“系统可以工作”，而是一个不看说明的观众能从 20–30 秒画面中理解：侧面是一组错落的立体模型，进入正确视角后它们突然成为一幅画。

## 一、核心假设

本周期验证五个假设：

1. 完整画面比坐标格更能产生创作感和视觉吸引力。
2. 固定尺寸的立体模型配合透视镜头，能让深度成为必要解法，而不是无意义的第三坐标。
3. 玩家能够通过直观控制理解“画面内位置”和“距离镜头远近”是两种不同操作。
4. 隐藏的物体 ID 与轮廓缓冲可以提供稳定、宽容的匹配，而不破坏参考画的艺术表现。
5. 从杂乱立体摆放到完整二维绘画的镜头揭晓，足以成为产品的核心传播瞬间。

任何一个假设失败，都优先修正它，不提前制作第二幅画、关卡系统或更多模型。

## 二、第一幅画：雾谷小桥

第一幅画使用项目原创构图，不直接采用真实名画或外部照片。这样可以控制可解性、避免素材授权问题，并让美术图和隐藏正确答案天然一致。

画面内容控制在八个可操纵单元：

- 太阳圆盘；
- 远山；
- 中景山体；
- 两组树丛；
- 小亭；
- 拱桥；
- 前景岩石。

水面、天空和雾作为固定舞台/环境，不作为可操纵单元。八个单元分布在至少三个明显深度层：

- 远景负责太阳和远山轮廓；
- 中景负责山体、树丛和小亭的叠压关系；
- 前景桥和岩石遮挡部分中景，并形成画面框景。

正确答案必须满足：从构图镜头看像一张风格化插画；从三分之四侧面看，模型的距离和相互关系明显不同于最终二维观感。

## 三、镜头原则

新场景有两个目的不同的镜头。

### 构建镜头

玩家主要通过三分之四视角观察和选择模型。它负责展示模型的实体感、深度轨道和桌面玩具质感，不负责最终匹配。

### 构图镜头

构图镜头必须是透视相机。它生成玩家当前画面、机器匹配缓冲和最终揭晓画面。移动模型远近必须改变屏幕中的表观大小。

旧原型使用正交投影；正交镜头中的深度不会改变物体大小，因此不能支撑这一核心玩法。旧镜头和方块场景保留，但不复用于新构图判断。

## 四、交互模型

第一版禁止自由缩放。每个模型有固定物理尺寸，玩家通过距离镜头的深度来改变表观大小。

建议控制：

- 左键点击：选择模型；
- 左键拖动：沿构图镜头的二维平面移动，使模型在画面中左右/上下变化；
- 鼠标滚轮：沿构图镜头前后移动，改变深度和表观大小；
- `Q` / `E`：在允许的单轴范围内旋转；
- `Z`：撤销；
- `R`：重置本幅画；
- 按住或切换一个观察键：临时强化构图镜头画面，但不提供复杂自由相机。

模型类别可以有不同约束：太阳允许在画面平面自由移动；桥、山体、亭子和树丛受舞台范围和最低高度限制。约束用于减少操作折磨，不用于偷偷吸附到答案。

第一版不加入三轴通用 Gizmo、任意旋转、自由缩放和自由相机。

## 五、目标图与机器真值

隐藏正确场景一次性生成三类资源：

1. `Beauty Reference`：玩家看到的完整风格化画面，包含材质、雾、灯光和背景。
2. `Object ID Reference`：每个可操纵单元使用稳定唯一颜色渲染，供机器比较归属和遮挡。
3. `Silhouette Reference`：所有可操纵景物合并为二值轮廓，供整体构图比较。

运行时构图镜头以低分辨率、无后处理方式生成当前 ID 和轮廓缓冲。评分不比较 Beauty Reference 的最终 RGB，因此调整灯光、雾和材质不会破坏解谜判定。

建议评分组成：

- 40%：整体轮廓 IoU；
- 45%：逐物体 ID 覆盖率的加权平均；
- 15%：关键遮挡/构图地标。

最终阈值先以调试数据确定，不提前锁死。初始目标为总分约 0.93，且每个关键物体不低于单独下限。使用宽容阈值而不是像素完全一致。

匹配频率控制在 5–10 Hz，并优先使用异步 GPU 回读，避免每帧同步读取 RenderTexture 导致卡顿。纯数组比较与评分权重放在可测试的项目自有 C# 逻辑中。

## 六、玩家看到的反馈

玩家不应该看到 ID 颜色、坐标格或工程化的逐像素差异。

场景提供两幅视觉信息：

- 一幅有实体画框的完整目标画；
- 一个由构图镜头实时输出的光学取景框。

接近目标时使用克制反馈：画框边缘逐渐闭合/点亮、重合区域轻微稳定、最偏离的模型在构建视角出现柔和提示。数字百分比只保留在开发调试模式，不作为主体验。

如果持续卡住，可以分阶段开启提示：先提示错误物体，再提示应向画面内哪个方向调整；不直接显示正确三维坐标。

## 七、成功揭晓

成功不是弹窗。顺序为：

1. 输入锁定，模型产生轻微落定反馈；
2. 构建镜头平滑移动到构图镜头位置；
3. 实时三维景物与 Beauty Reference 进行短暂视觉融合；
4. 画框、雾和光线完成一次克制的收束；
5. 保持足够时间让玩家看清完整画面；
6. 可选地缓慢移回侧面，揭示为了成画而形成的奇特空间布局。

最终录屏必须仅靠这个过程就能说明玩法。

## 八、任务顺序与硬门槛

### T-008：隐藏正确场景与目标资源

先做非交互视觉真相。创建独立 `PaintingPrototype` 场景及确定性构建工具，生成 Beauty、ID、Silhouette 三类资源和正面/侧面审查图。

硬门槛 A：用户与 Codex 都认为正面是一幅画、侧面是一组真实立体模型。未通过则只修改构图与美术，不开发操作系统。

### T-009：目标数据与宽容评分器

实现机器真值格式、低分辨率当前缓冲和纯逻辑评分。用正确答案、水平偏移、垂直偏移、深度错误和遮挡错误建立确定性测试样例。

硬门槛：正确解稳定通过；不同错误主要降低对应评分；运行时采样没有明显卡顿。

### T-010：透视模型操纵

实现选择、构图平面拖动、深度滚轮、约束旋转、撤销和重置。新系统与旧 Voxel/Grid 领域分离，不为兼容旧关卡扭曲新模型。

硬门槛 B：不打开 Inspector，测试者能够把一个打乱的三物体小样恢复到目标构图，并明确感受到深度改变大小。

### T-011：完整画面反馈

接入目标画框、实时取景框、匹配状态和分级提示。首先解决“玩家知不知道差在哪里”，再调 UI 质感。

### T-012：揭晓与产品级呈现

实现镜头融合、落定反馈、雾光收束和侧面反揭示。输出 20–30 秒无旁白视频所需的稳定画面。

### T-013：验证构建

补齐 EditMode/PlayMode 测试、确定性截图、Windows 构建和启动测试。最终必须由用户直接试玩。

硬门槛 C：试玩后只回答三件事——是否想继续摆第二幅画、最难理解的操作是什么、揭晓是否值得录屏。没有肯定证据时不扩展内容。

## 九、时间与代理分工

预计六个实现/审查区块，每个约 1.5–3 小时，总计约 12–20 小时墙钟时间；视觉构图返工可能增加时间，但不会跳过硬门槛。

Codex 负责：

- 每个任务前的产品、接口、坐标和验收设计；
- 目标构图审查；
- 评分算法与关键边界的最终审查；
- Unity 编译、测试、截图和构建验收；
- 将错误缩成下一个 `tasks/ACTIVE.md`。

DeepSeek V4 Flash 负责：

- 已指定算法的编辑器场景生成代码；
- 渲染缓冲、数据类型和局部评分实现；
- 已定义控制方式的运行时代码；
- 聚焦测试和明确错误的修复。

连续任务复用同一个 Claude Code 会话。DeepSeek 每次只接收 `tasks/ACTIVE.md` 中一个可审查合同，不让它同时决定产品、美术、架构和实现。

## 十、明确不做

本周期不做：

- 第二幅或第三幅画；
- 名画授权、照片导入和任意图片自动生成关卡；
- 通用计算机视觉或神经网络匹配；
- 多视角同时匹配；
- 自由相机和专业三维编辑器式 Gizmo；
- 自由缩放；
- 关卡选择、存档、账号、联网和玩家创作；
- 高成本角色、叙事、配音和完整音频系统；
- 为旧 5×5 方块玩法继续制作内容。

## 十一、周期结束的决策

周期结束后只允许三种决策：

1. `GO`：核心操作清楚、构图过程有趣、揭晓成立，开始设计第二幅画和可复用内容管线。
2. `ITERATE`：视觉命题成立，但操作或评分令人挫败，再做一个专门修正周期。
3. `STOP/PIVOT`：即使正确呈现仍缺乏乐趣或惊喜，保留技术资产，不继续扩大项目。

当前 `tasks/ACTIVE.md` 保持 `IDLE`。只有 T-008 的具体场景、文件和验收合同写清楚后，才启动 DeepSeek 实现。
